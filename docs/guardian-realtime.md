# 보호자 홈·신호와 실시간 갱신

브랜치: `feat/guardian-home-realtime`.

## 구현

- 로그인한 보호자의 ACTIVE 연결로 홈 요약·신호 목록·최근 활동을 읽는다. 기기 연결 여부는 서버의 connection.state를 사용한다.
- 보내기 시트에서 실제 메시지 생성 API를 호출하고 기기 전달과 터치 응답을 따로 표시한다. HTTP 201이어도 delivery.FAILED면 실패로 표시한다.
- 전송 결과가 불명확한 네트워크 실패는 같은 Idempotency-Key로 재시도한다. 연속 탭은 같은 진행 중 요청을 공유한다.
- 신호 상세는 서버의 신호 이름·설명·리듬을 사용한다. 응답 없음 상세는 해당 메시지 ID와 서버 타임라인을 사용하며 재전송 후 새 메시지 상세로 이동한다. 서버가 허용할 때만 대기 연장을 제공한다.
- 홈에서 여는 기록 목록도 날짜별 실제 기록 API를 사용한다. 도움 요청은 열람 확인을 기록하고, 공유된 위치와 후속 신호를 표시한다.
- `src/realtime/`은 expo/fetch의 스트리밍 GET `/events`를 사용한다. Bearer 헤더·Last-Event-ID, UTF-8 분할, SSE 프레임, 중복 방지, 지수 재연결과 45초 무응답 감지를 처리한다.
- message.updated는 보호자 메시지 스토어와 홈/기록 조회를 갱신한다. message.created는 당사자의 기존 `handleIncoming`을 사용한다. FCM 연결 코드에서도 같은 함수를 호출할 수 있다.
- 백그라운드·로그아웃 시 스트림과 조회를 중지한다. 계정/연결이 바뀐 뒤 이전 결과를 적용하지 않는다. 놓친 이벤트는 재접속 때 조회하며, 활성 상태에서 5초 간격으로 복구 조회한다.
- 기존 서버 없는 개발용 화면 미리보기는 별도 preview 파일에 유지한다. 실제 로그인 상태에서는 모의 데이터를 사용하지 않는다.

## 현재 백엔드와 확인 범위

2026-11-11 로컬 backend dev `2247547`에서 홈·신호 목록·메시지 생성/상세·재전송(같은 키 재요청)·ack·재생 보고·터치 응답·도움 요청 열람과 SSE 접속/heartbeat를 확인했다. 테스트 연결은 종료하고 테스트 세션은 로그아웃했다.

이 dev에는 SSE endpoint/hub는 있지만 도메인 이벤트 발행이 없다. 발행 구현은 원격 `feat/95-sse-publishing`에 있으므로 해당 변경이 백엔드 실행 브랜치에 합쳐져야 실제 이벤트로 즉시 갱신되는 것까지 검증할 수 있다. 현재 dev에서도 5초 복구 조회로 갱신한다. 백엔드 브랜치는 변경하지 않았다.

현재 dev 홈 위치 요약은 sharingEnabled:false 고정이다. 별도 연습 신호 생성 API도 없어 실제 신호 상세에서 연습 전송 성공을 표시하지 않는다. FCM 등록/수신과 실기기 진동은 이 변경의 검증 범위에 포함하지 않는다.

## 확인 방법

1. 로컬 Docker 백엔드와 개발 서버를 실행한다. 휴대폰이 접근할 수 있는 PC 주소를 `.env.local`의 EXPO_PUBLIC_API_URL에 설정한다.
2. 보호자/당사자로 로그인해 연결한다. 보호자 홈의 이름·신호 목록·최근 기록을 확인한다.
3. 신호를 보내고 전달 상태를 확인한다. 당사자 앱에서 수신 화면을 터치하면 보호자 시트/홈/상세가 응답 완료로 바뀌는지 확인한다.
4. 실제 서버가 NO_RESPONSE로 판정한 메시지를 열어 다시 보내고 새 메시지 상세로 이동하는지 확인한다.
5. 두 앱을 전환하거나 네트워크를 끊었다 복원한 뒤 놓친 상태가 갱신되는지 확인한다.

자동 검증: `npm test`, `npm run lint`, `npm run typecheck`. Android 번들: `npx expo export --platform android --clear --output-dir .expo/guardian-verification`.
